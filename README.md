# Draft

Инструмент для организации разрозненных идей и черновиков: карточки-фрагменты,
которые можно копить без давления немедленной структуры, и просматривать в
разных "видах" одних и тех же данных — облако и таймлайн. Слева — дерево
проектов (Obsidian-style): части, главы, сцены — произвольной вложенности,
каждый узел дерева — самостоятельный проект со своим облаком и таймлайном.

Это MVP по брифу (см. `BRIEF.md`, если сохранён в репозитории/задаче) — auth,
CRUD карточек, облако на d3-force, таймлайн, анимированное переключение
между видами, полноэкранный редактор карточки, дерево проектов в сайдбаре.

## Стек

- React + Vite (TypeScript)
- `d3-force` — force-directed layout облака
- `dnd-kit` — drag & drop в таймлайне (ручной порядок карточек)
- `framer-motion` — анимация переключения между видами (`layout`/`layoutId`)
  и полноэкранного редактора карточки
- Supabase (Postgres + Auth) — бэкенд
- Vercel — хостинг (деплой как обычное Vite-приложение)

## Быстрый старт

```bash
npm install
npm run dev
```

По умолчанию (без переменных окружения) приложение работает в **локальном
режиме**: данные хранятся в `localStorage` браузера, "вход" — по email без
подтверждения. Это сделано специально, чтобы UI можно было собирать и
пробовать без настроенного Supabase-проекта.

### Подключение Supabase

1. Создайте проект в Supabase, примените схему из `supabase/schema.sql`
   (SQL Editor → вставить и выполнить). Если проект уже существовал до
   появления дерева проектов — примените ещё и
   `supabase/migrations/002_project_hierarchy.sql` (добавляет `parent_id`).
2. Скопируйте `.env.example` в `.env.local` и заполните
   `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (Project Settings → API).
3. В Supabase Auth включите Email OTP / magic link (по умолчанию включено).
4. `npm run dev` — теперь приложение работает через реальный бэкенд.

## Модель данных

См. `supabase/schema.sql`. Таблицы: `projects` (само-ссылающаяся через
`parent_id` — дерево произвольной глубины), `cards`, `card_links`
(база под ручные связи заложена, но UI для них в MVP не реализован — вне
скоупа первой итерации).

## Ключевые технические решения

- **Облако**: `d3-force` симуляция (`forceManyBody` — отталкивание,
  `forceCollide` — не накладываются, `forceX`/`forceY` со слабой силой —
  мягкий якорь к центру холста, `forceLink` подключён с пустым списком
  связей — готов для второй итерации). Перетаскивание карточки выполняется
  обычными pointer-событиями (не через dnd-kit) — это стандартный паттерн
  для физической симуляции, где на каждый кадр нужно напрямую двигать
  `fx`/`fy` узла; dnd-kit используется в таймлайне, где drag — это
  дискретная пересортировка списка, а не непрерывная физика.
- **Таймлайн**: `dnd-kit` (`DndContext` + `SortableContext`, два контейнера —
  упорядоченный сюжет и зона "пока вне сюжета"). Ручной порядок пишется в
  `manual_order`; карточки без ручного порядка не считаются частью сюжета
  и не сортируются принудительно.
- **Переключение видов**: каждая карточка — один и тот же `motion.div` с
  `layoutId`, только с разным способом позиционирования в зависимости от
  вида. Framer Motion сам анимирует переезд (FLIP) между позициями.
- **Первый запуск**: без выбора жанра/шаблона — сразу текстовое поле и
  кнопка «Добавить карточку» (антипаттерны из брифа намеренно не
  реализованы: не спрашиваем структуру, не мигрируем данные при
  переключении видов, не создаём связи автоматически на основе смысла
  карточек).
