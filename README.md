# Draft

Инструмент для организации разрозненных идей и черновиков: карточки-фрагменты,
которые можно копить без давления немедленной структуры, и просматривать в
разных "видах" одних и тех же данных — облако и таймлайн. Слева — дерево
проектов (Obsidian-style): части, главы, сцены — произвольной вложенности,
каждый узел дерева — самостоятельный проект со своим облаком и таймлайном.

Это MVP по брифу (см. `BRIEF.md`, если сохранён в репозитории/задаче) — auth,
CRUD карточек, облако на d3-force, таймлайн, анимированное переключение
между видами, полноэкранный редактор карточки, дерево проектов в сайдбаре.

## Стек

- React + Vite (TypeScript)
- `d3-force` — force-directed layout облака
- `dnd-kit` — drag & drop в таймлайне (ручной порядок карточек)
- `framer-motion` — анимация переключения между видами (`layout`/`layoutId`)
  и полноэкранного редактора карточки
- Supabase (Postgres + Auth) — бэкенд
- Vercel — хостинг (деплой как обычное Vite-приложение)

## Быстрый старт

```bash
npm install
npm run dev
```

По умолчанию (без переменных окружения) приложение работает в **локальном
режиме**: данные хранятся в `localStorage` браузера, "вход" — по email без
подтверждения. Это сделано специально, чтобы UI можно было собирать и
пробовать без настроенного Supabase-проекта.

### Подключение Supabase

1. Создайте проект в Supabase, примените схему из `supabase/schema.sql`
   (SQL Editor → вставить и выполнить). Если проект уже существовал до
   появления дерева проектов — примените ещё и
   `supabase/migrations/002_project_hierarchy.sql` (добавляет `parent_id`).
2. Скопируйте `.env.example` в `.env.local` и заполните
   `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (Project Settings → API).
3. В Supabase Auth включите Email OTP / magic link (по умолчанию включено).
4. `npm run dev` — теперь приложение работает через реальный бэкенд.

## Модель данных

См. `supabase/schema.sql`. Таблицы: `projects` (само-ссылающаяся через
`parent_id` — дерево произвольной глубины), `cards`, `card_links`
(база под ручные связи заложена, но UI для них в MVP не реализован — вне
скоупа первой итерации).

## Структура

```
src/
  types.ts              — доменные типы (Card, Project, CardStatus, …)
  lib/
    supabase.ts          — клиент Supabase (или null, если не настроен)
    dataStore.ts         — интерфейс DataStore + выбор реализации
    supabaseStore.ts      — реализация поверх Supabase
    localStore.ts         — реализация поверх localStorage (дев-режим)
    timeline.ts           — сортировка карточек для таймлайна
  hooks/
    useAuth.ts, useCards.ts
    useProjectTree.ts      — дерево проектов + какой проект сейчас открыт
    useCloudSimulation.ts — обёртка над d3-force для облака
    useElementSize.ts
  components/
    AuthScreen, EmptyProjectScreen  — экраны 5.1
    Sidebar, ProjectTreeItem        — дерево проектов слева
    CloudView                      — облако, экран 5.2
    TimelineView                   — таймлайн, экран 5.3
    BoardView, ViewSwitcher (вкладки), PreviewBar — экран 5.4
    CardTile, StatusPicker, CardEditor — карточка и полноэкранный редактор
```

## Ключевые технические решения

- **Облако**: `d3-force` симуляция (`forceManyBody` — отталкивание,
  `forceCollide` — не накладываются, `forceX`/`forceY` со слабой силой —
  мягкий якорь к центру холста, `forceLink` подключён с пустым списком
  связей — готов для второй итерации). Перетаскивание карточки выполняется
  обычными pointer-событиями (не через dnd-kit) — это стандартный паттерн
  для физической симуляции, где на каждый кадр нужно напрямую двигать
  `fx`/`fy` узла; dnd-kit используется в таймлайне, где drag — это
  дискретная пересортировка списка, а не непрерывная физика.
- **Таймлайн**: `dnd-kit` (`DndContext` + `SortableContext`, два контейнера —
  упорядоченный сюжет и зона "пока вне сюжета"). Ручной порядок пишется в
  `manual_order`; карточки без ручного порядка не считаются частью сюжета
  и не сортируются принудительно.
- **Переключение видов**: каждая карточка — один и тот же `motion.div` с
  `layoutId`, только с разным способом позиционирования в зависимости от
  вида. Framer Motion сам анимирует переезд (FLIP) между позициями.
- **Первый запуск**: без выбора жанра/шаблона — сразу текстовое поле и
  кнопка «Добавить карточку» (антипаттерны из брифа намеренно не
  реализованы: не спрашиваем структуру, не мигрируем данные при
  переключении видов, не создаём связи автоматически на основе смысла
  карточек).

## Десктоп-версия (Windows/Mac, Tauri)

Тот же фронтенд, обёрнутый в нативное окно через [Tauri](https://tauri.app/)
(`src-tauri/`) — без подписки, без сервера, данные полностью локальны.

### Разработка

```bash
npm run desktop:dev     # запускает vite + открывает нативное окно
npm run desktop:build   # собирает установщик для ТЕКУЩЕЙ ОС
```

Сборка кросс-платформенная только через нативные раннеры — собрать `.dmg`
или `.msi` с Linux/из этой песочницы нельзя (Tauri встраивает WebView2
на Windows и WKWebView на Mac — их не скрестировать). Для этого есть workflow
`.github/workflows/build-desktop.yml`:

- **Actions → Build desktop app → Run workflow** — соберёт `.dmg` (Mac,
  universal) и `.msi`/`.exe` (Windows), результат — файлы в артефактах запуска.
- Пуш тега `v1.0.0` — то же самое, плюс создаст черновик GitHub Release с
  установщиками во вложении.

Сборки пока **без подписи кода** — при установке система покажет
предупреждение «неизвестный разработчик» (Mac) / «Windows защитила ваш
компьютер» (Windows), которое можно обойти вручную. Подпись — это
Apple Developer Program ($99/год, нужен для notarization на Mac) и
платный сертификат для Windows; добавить её в `build-desktop.yml`
можно в любой момент, когда решите продавать всерьёз.

### Данные

Десктоп-сборка **всегда** хранит данные локально — файл `draft-data.json`
в системной папке данных приложения (`~/Library/Application Support/`
на Mac, `%APPDATA%` на Windows), через `@tauri-apps/plugin-store`. Supabase
не участвует вообще, даже если случайно оказался сконфигурирован
(`src/lib/dataStore.ts` проверяет `isTauri()` первым делом). Веб-версия
на Vercel как работала на Supabase/localStorage, так и работает —
десктоп-ветка кода её не касается.

### Лицензии — офлайн, без сервера

Активация — один ключ, который проверяется **локально** по ECDSA-подписи
(`src/lib/license.ts`); ни при активации, ни потом приложение никуда не
стучится.

```bash
npm run license:keypair                          # один раз — создаёт пару ключей
npm run license:generate -- --email buyer@mail.ru [--order 123]
```

- `license:keypair` кладёт приватный ключ в `private/license-private-key.json`
  (в `.gitignore`, никогда не коммитится) и печатает публичный ключ — его
  нужно вставить в `PUBLIC_KEY_JWK` в `src/lib/license.ts` (это уже сделано
  для сгенерированной сейчас пары).
- `license:generate` — запускаете сами, офлайн, при каждой продаже; выводит
  готовый ключ для покупателя.
- `license:generate -- --email test@mail.ru --trial-days 7` — пробный ключ:
  тот же формат, но с `expiresAt` внутри подписанного payload, так что срок
  нельзя продлить без приватного ключа. Приложение сверяет его при каждом
  запуске и раз в 30 минут, пока открыто; сайдбар показывает, сколько дней
  осталось.

**Приватный ключ существует только в двух местах: файл `private/` в этой
рабочей копии и то, что я вам передам в чате.** Раз он в `.gitignore` — он
не уйдёт в GitHub. Сохраните его прямо сейчас в password-менеджер или
отдельный зашифрованный бэкап: потеряете — не сможете выпускать новые
ключи (уже выданные при этом продолжат работать вечно, они не привязаны
к серверу). Если ключ утечёт — тоже плохо: тогда лицензии сможет
генерировать кто угодно. Скомпрометировали — перегенерируйте пару
(`license:keypair`) и обновите `PUBLIC_KEY_JWK` в новой версии приложения;
старые ключи при этом перестанут подходить к новым сборкам.

### Продажа — страница на /buy, автоматическая выдача ключа

`public/buy.html` (открывается по адресу `/buy`) — страница продажи рядом
с веб-версией: описание, цена, форма с почтой. При отправке формы:

1. `api/create-payment.ts` создаёт платёж в ЮKassa и отдаёт ссылку на
   оплату (сумма всегда берётся из переменных окружения на сервере —
   покупатель не может подменить цену в запросе).
2. Покупатель платит на стороне ЮKassa и возвращается на `/thank-you`.
3. ЮKassa шлёт вебхук на `api/yookassa-webhook.ts`. Обработчик
   перезапрашивает платёж у самой ЮKassa (не доверяет телу вебхука
   напрямую), подписывает новый лицензионный ключ **тем же приватным
   ключом**, что и `license:generate`, но теперь он живёт в переменной
   окружения на Vercel, а не только офлайн — это единственный способ
   выдавать ключи автоматически, без вашего участия при каждой продаже.
   Заказ и ключ пишутся в таблицу `license_orders` в Supabase (миграция
   `004_license_orders.sql`) — это и защита от повторной выдачи при
   повторе вебхука, и журнал продаж.
4. Ключ и ссылки на установку уходят на почту письмом через Resend.

Репозиторий приватный, поэтому прямая ссылка на GitHub Release не
работает для покупателя без доступа к репозиторию — `api/download.ts`
это обходит: проверяет лицензионный ключ на сервере, затем сам, с токеном
GitHub, спрашивает у GitHub временную (публичную) ссылку на нужный файл
установки и отдаёт покупателю её. Поэтому после каждого релиза через
`build-desktop.yml` черновик (**draft**) нужно вручную опубликовать в
GitHub — пока он черновик, `/releases/latest` его не видит, это и есть
точка ручной проверки перед тем, как файлы станут доступны на скачивание.

Переменные окружения, которые нужно завести в Vercel (Project Settings ->
Environment Variables) — ни одна из них не должна начинаться с `VITE_`,
иначе она попадёт в код, отдаваемый браузеру:

| Переменная | Для чего |
| --- | --- |
| `YOOKASSA_SHOP_ID`, `YOOKASSA_SECRET_KEY` | доступ к API ЮKassa (Личный кабинет -> Настройки) |
| `LICENSE_PRICE_VALUE`, `LICENSE_PRICE_CURRENCY` | цена (например `2900.00` / `RUB`) — сейчас в коде placeholder, поменяйте на реальную |
| `LICENSE_PRIVATE_KEY_JWK` | JSON приватного ключа — то же значение, что лежит в `private/license-private-key.json` в поле `privateKey`, одной строкой |
| `SUPABASE_SERVICE_ROLE_KEY` | сервисный ключ того же проекта Supabase (Project Settings -> API) — обходит RLS, чтобы вебхук мог писать заказы |
| `RESEND_API_KEY`, `RESEND_FROM` | отправка письма с ключом (`RESEND_FROM` — адрес на домене, подтверждённом в Resend) |
| `GITHUB_TOKEN` | токен с доступом на чтение содержимого приватного репозитория — для выдачи ссылок на установщики |

И в личном кабинете ЮKassa нужно указать адрес вебхука:
`https://<ваш-домен>/api/yookassa-webhook`, событие `payment.succeeded`.

Готового автотеста платежа нет — оплатить по-настоящему может только
живой аккаунт ЮKassa. Логика подписи ключа, выдачи установщика и разбора
цены проверена локально мок-запросами; после того как впишете реальные
ключи в Vercel, стоит один раз пройти покупку целиком на небольшую сумму.
